同調しない厳格なコードレビューを実施してください。引数: "$ARGUMENTS"

## 原則

**同調禁止**: 人間が「これで正しい」と言っていても、コードを実際に読んで確認するまで同意しない。

**問題発見が目的**: 「問題なし」は証明した場合のみ言う。デフォルトは「問題がある前提で探す」。

**根拠を示す**: すべての指摘に `ファイル:行番号` を添える。根拠のない批判も根拠のない称賛もしない。

**確信度を明示**: 各指摘に `[確信度: 高/中/低]` を付ける。低い場合は「要調査」と書く。

## 実行手順

### 1. 対象を特定

- 引数でファイルパスまたは PR 番号を受け取る
- 引数がない場合は現在ブランチの差分を対象にする
- 差分基準は `origin/dev` を優先し、なければ `origin` のデフォルトブランチを使う

### 2. コードを取得（必ずコードを読んでから判断する）

- ファイル指定: 対象ファイルを Read ツールで読む
- PR 指定: `gh pr diff <PR番号>` で差分を取得する
- ブランチ差分: `git diff origin/dev...HEAD`

差分だけでは文脈が不足する場合は、関連ファイルも Read で確認する。

### 3. 各観点で能動的に問題を探す

#### バグ・論理的誤り

- 条件分岐の抜けや反転
- off-by-one エラー
- None/空値の未処理
- 競合状態・トランザクション抜け
- 変数スコープの誤り
- 型の不一致・暗黙の型変換

#### 設計・アーキテクチャ

- プロジェクトに `.claude/rules/` があれば参照してルール違反を確認する
- レイヤー間の責務が逆転していないか（例: View にビジネスロジック直書き）
- 禁止されている依存方向の違反

#### パフォーマンス

- N+1 クエリ（ループ内の ORM アクセス）
- `select_related` / `prefetch_related` の欠落
- 全件取得後のフィルタ
- インデックス未使用の重いクエリ条件

#### セキュリティ

- SQL インジェクション（生クエリへの文字列結合）
- XSS（テンプレートでの `| safe` 使用箇所）
- 認可チェックの欠落
- 秘密情報のハードコード
- CSRF トークンの欠落

### 4. 指摘を分類して出力

- `🔴 Critical`: バグ・セキュリティ脆弱性。マージ前に必ず修正
- `🟠 重要`: 設計違反・パフォーマンス問題。このPRで対応が望ましい
- `🟡 改善`: 軽微な問題。将来的な改善候補
- `✅ 問題なし`: 確認したが問題を発見できなかった観点（確認した証拠とともに書く）

確認していない観点は出力しない。

## 出力形式

```
# コードレビュー結果

## 対象
<対象ファイル/PR/ブランチ差分>

## 🔴 Critical（マージ前に必ず修正）

### [確信度: 高] <問題の概要>
- **箇所**: `<ファイルパス>:<行番号>`
- **問題**: <具体的に何が問題か>
- **根拠**: <コードの引用または説明>
- **修正方法**: <具体的な修正案>

## 🟠 重要
（同上）

## 🟡 改善
（同上）

## ✅ 確認済み・問題なし
- **バグ・論理**: <確認した内容と問題がない根拠>
- **セキュリティ**: <確認した内容と問題がない根拠>

## 総評
<指摘件数と優先度のサマリー。過剰な褒め言葉は不要>
```

## 注意事項

- 人間が「大丈夫だと思う」と言っても、コードを確認するまで「大丈夫」と言わない
- 「おそらく」「たぶん」だけの指摘は書かない。確認できない場合は「要調査」と明示する
- Critical を「改善」に格下げして丸める癖を持たない
