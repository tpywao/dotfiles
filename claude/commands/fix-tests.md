変更に関連する Django テストを走らせ、緑になるまで修正する。引数: "$ARGUMENTS"

## 対象の決定

- 引数があればそれをテスト対象にする(アプリ名 / モジュールパス / テストクラス・メソッド)。
- 引数が無ければ、現在ブランチの差分(`git diff` の変更ファイル)から関連する Django アプリ/モジュールを推定して対象にする。範囲が不明なら対象を `AskUserQuestion` で確認する。

## 実行

- テストは `python manage.py test <対象>` で走らせる。プロジェクトが uv 運用なら `uv run python manage.py test <対象>` を使う(どちらかは既存の運用に合わせる)。
- まず対象を絞って実行し、全体実行は最後の確認に使う(高速なフィードバックループを優先)。

## 修正ループ

1. テストを実行する。
2. 失敗したら、スタックトレース・アサーション内容を読み、**実装側の原因**を特定する(該当コードを Read で確認する)。
3. 原因に対する**最小限の修正**を行う。
4. 再実行する。緑になるまで 2〜4 を繰り返す。
5. 最後に対象範囲のテストを通しで実行し、全て緑であることを確認する。

## 鉄則

- **テストを通すためにテストを弱めない**。アサーションの削除・緩和、`skip`/`xfail` の付与、テストのコメントアウトで「緑に見せる」ことは禁止。
- テスト自体が誤っていると判断した場合は、勝手に書き換えず**根拠とともに指摘**し、どう直すべきか提案して判断を仰ぐ。
- モデル変更でマイグレーションが必要なら `python manage.py makemigrations` で正規生成する(手書きしない)。
- 数回繰り返しても緑にできない場合は、無理に変更を重ねず、**何がどう失敗しているか・原因の仮説・行き詰まっている点**を整理して報告する。

## 出力

- 実行したテストコマンドと最終結果(成功/失敗の件数)。
- 加えた修正の要点(`ファイル:行番号` と理由)。
- 通せなかった場合は失敗内容と原因の仮説。
