# QA へのテスト依頼

## 概要

QA はテスト項目を上から順に画面で操作し、結果を書き足して返す。書かれていない前提（どのアカウントを使うか、そのアカウントで画面がどう見えるのが正常か、操作後に状態をどう戻すか）は QA が自分で決めるしかなく、そこで迷うか、誤って不具合として報告される。

このスキルは、その前提をすべて本文に書き出した依頼文を作る。

`qa-handoff`（applynow の `.claude/skills/qa-handoff/SKILL.md`）の制約とスタイルを前提にする。GitHub を参照しない、QA 向けの本文に SQL やモデル名を書かない、実装用語を画面の言葉に置き換える、などがそれにあたる。スキル一覧に無ければ `~/apn/applynow/.claude/skills/qa-handoff/SKILL.md` を Read してから書く。

## 手順

1. 変更した条件分岐を列挙する。確認項目は各分岐を 1 回ずつ通すケースだけにし、同じ処理に合流する入口違いや自動テストで確かめた性質は入れない
2. 下の構成でテスト項目のコメントを書く
3. ユーザーに文面を見せ、承認を得てから Backlog に投稿する
4. 投稿後、依頼のコメントを別に投稿する（下の「依頼のコメント」）

## テスト項目のコメントの構成

```markdown
## <機能名>の UI テスト項目

test 環境（https://test.applynow.jp）で画面を操作して確認する項目です。<対象外の範囲と理由。例: 企業ユーザーはほとんどが PC から使うため、スマホ幅の表示は対象外としています>

### 準備するデータ

<既存データで足りるならそれを勧める一文。例: 企業「株式会社ApplyNow」には X1〜X3 に当てはまるユーザーがそろっているので、新しく作る必要はありません>

| No | 用意するもの | 内容 |
|---|---|---|
| P1 | スタッフA | <条件> |
| P2 | X1 | 企業X の企業ユーザー。<条件> |

### テスト項目

1. 【<区分>】<操作するアカウントの呼び名>: <手順>
   - 期待結果: <画面に出る文言を「」で引用して書く>

### 開発者が確認する項目

画面には表示されないため、開発者が確認します。

- <DB やログでしか確かめられない項目>
```

各部分で必ず入れるもの:

- **準備データの呼び名**: アカウントやデータに「スタッフA」「X1」のような呼び名と番号（P1〜）を付け、テスト項目では呼び名だけで指す。手順の中で条件を毎回書き直さない
- **権限を絞ったアカウントの用意の仕方と見え方**: 権限の有無で結果が変わるアカウントには、どこでどの権限を付ける・外すかを書く。そのアカウントでログインしたときに画面全体がどう見えるのが正常かも書く（例:「メニューがほとんど表示されないのは正常です」）。書かないと、QA は画面の異常か準備の誤りかを判断できない
- **前の項目の参照**: 同じ画面や操作を続けて使うときは「No.1 の画面で」「No.7 の操作のあと」と番号で指す
- **出ないのが正しい項目**: 期待結果に「（仕様。<理由>）」を添える。理由が無いと、QA は仕様か不具合かを判断できない
- **状態を変える項目の戻し方**: 公開・非公開、ログイン中、設定値など、後の項目や他の人の作業に残る状態を変えるときは、期待結果のあとに戻し方を書く（例:「確認後は No.12 の手順で終了する」「確認後は求人を公開に戻す」）
- **確認範囲が QA によって変わる項目**: 「複数の画面を開く」のように範囲を QA が選ぶ項目は、「確認した画面名を結果に書いてください」と頼む
- **開発者が確認する項目**: DB の列の値やログなど画面に出ないものは、本文から落とさずにこの節に残す。何をどの値と比べるかを 1 行で書く。該当が無ければ節ごと省く

## 依頼のコメント

テスト項目とは別のコメントにする。テスト項目のコメントは、QA が結果を書き込むためにそのまま複製する元になるので、依頼の文言を混ぜない。

```markdown
@<QA 担当者>
テスト環境にデプロイしたため、テストお願いします！ :bow:

https://opencloud.backlog.com/view/APN-XXXX#comment-<テスト項目のコメント ID>
↑こちらにテスト手順を記載しましたので確認・実施お願いします！
```

投稿と同時に担当者を QA に変える。QA 担当者が分からなければユーザーに確認する。

## よくある間違い

- 準備データを「管理者権限なし 1 名」のように条件だけで書き、用意の仕方を書かない → QA は手近なアカウントを選び、想定と違う権限で確かめる
- DB でしか確認できない値を、QA 向けではないからと文面ごと落とす → 誰も確認しないまま終わる。「開発者が確認する項目」に残す
- 依頼とテスト項目を 1 つのコメントにまとめる → QA が複製して結果を書くときに、依頼の文言まで写る
