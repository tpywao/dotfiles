# QA へのテスト依頼

## 概要

QA はテスト項目を上から順に画面で操作し、結果を書き足して返す。書かれていない前提（どのアカウントを使うか、そのアカウントで画面がどう見えるのが正常か、操作後に状態をどう戻すか）は QA が自分で決めるしかなく、そこで迷うか、誤って不具合として報告される。

このスキルは、その前提をすべて本文に書き出した依頼文を作る。

## 手順

1. プロジェクトに固有の値を集める。プロジェクトの指示ファイルやリファレンス用のスキルに書いてあるものを使い、無ければユーザーに聞く
   - テスト環境の URL
   - チケット管理サービスと記法、コメントの URL の形式、メンションの書き方
   - QA の担当者
   - QA 向けの文章の制約（参照できないサービス、使わない用語など）。プロジェクトにそれを定めたスキルがあれば先に読む
   - 準備データに使える既存の組織・ユーザー
2. 変更した条件分岐を列挙する。確認項目は各分岐を 1 回ずつ通すケースだけにし、同じ処理に合流する入口違いや自動テストで確かめた性質は入れない
3. 下の構成でテスト項目のコメントを書く
4. ユーザーに文面を見せ、承認を得てから投稿する
5. 投稿後、依頼のコメントを別に投稿する（下の「依頼のコメント」）

## テスト項目のコメントの構成

```markdown
## <機能名>の UI テスト項目

テスト環境（<URL>）で画面を操作して確認する項目です。<対象外の範囲と理由。例: 利用者はほとんどが PC から使うため、スマホ幅の表示は対象外としています>

### 準備するデータ

<既存データで足りるならそれを勧める一文。例: 組織「<名前>」には X1〜X3 に当てはまるユーザーがそろっているので、新しく作る必要はありません>

| No | 用意するもの | 内容 |
|---|---|---|
| P1 | 担当者A | <条件と用意の仕方> |
| P2 | X1 | 組織X のユーザー。<条件> |

### テスト項目

| No | 区分 | 操作するアカウント | 手順 | 期待結果 |
|---|---|---|---|---|
| 1 | <区分> | 担当者A | <手順> | <画面に出る文言を「」で引用して書く> |

### 開発者が確認する項目

画面には表示されないため、開発者が確認します。

- <DB やログでしか確かめられない項目>
```

テスト項目を表にするのは、QA がこのコメントを複製し、結果・スクリーンショット・コメントの列を足して返すため。番号付きのリストでは列を足せない。

各部分で必ず入れるもの:

- **準備データの呼び名**: アカウントやデータに「担当者A」「X1」のような呼び名と番号（P1〜）を付け、テスト項目では呼び名だけで指す。手順の中で条件を毎回書き直さない
- **権限を絞ったアカウントの用意の仕方と見え方**: 権限の有無で結果が変わるアカウントには、どこでどの権限を付ける・外すかを書く。そのアカウントでログインしたときに画面全体がどう見えるのが正常かも書く（例:「メニューがほとんど表示されないのは正常です」）。書かないと、QA は画面の異常か準備の誤りかを判断できない
- **前の項目の参照**: 同じ画面や操作を続けて使うときは「No.1 の画面で」「No.7 の操作のあと」と番号で指す
- **出ないのが正しい項目**: 期待結果に「（仕様。<理由>）」を添える。理由が無いと、QA は仕様か不具合かを判断できない
- **状態を変える項目の戻し方**: 公開・非公開、ログイン中、設定値など、後の項目や他の人の作業に残る状態を変えるときは、期待結果のあとに戻し方を書く（例:「確認後は No.12 の手順で終了する」「確認後は記事を公開に戻す」）
- **確認範囲が QA によって変わる項目**: 「複数の画面を開く」のように範囲を QA が選ぶ項目は、「確認した画面名を結果に書いてください」と頼む
- **開発者が確認する項目**: DB の列の値やログなど画面に出ないものは、本文から落とさずにこの節に残す。何をどの値と比べるかを 1 行で書く。QA が状態を戻すとその値が消える・書き換わるなら、その項目の戻し方に「開発者が確認するまで戻さずに残してください」と添える。該当が無ければ節ごと省く

## 依頼のコメント

テスト項目とは別のコメントにする。QA はテスト項目のコメントを複製して結果を書き込むので、依頼の文言を混ぜない。

依頼のコメントには次の 3 つだけを書く。

- QA 担当者へのメンション
- テスト環境にデプロイしたことと、テストのお願い
- テスト項目のコメントへのリンク

投稿と同時にチケットの担当者を QA に変える。

## よくある間違い

- 準備データを「管理者権限なし 1 名」のように条件だけで書き、用意の仕方を書かない → QA は手近なアカウントを選び、想定と違う権限で確かめる
- DB でしか確認できない値を、QA 向けではないからと文面ごと落とす → 誰も確認しないまま終わる。「開発者が確認する項目」に残す
- 依頼とテスト項目を 1 つのコメントにまとめる → QA が複製して結果を書くときに、依頼の文言まで写る
