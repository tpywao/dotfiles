# PR セルフチェック

## 概要

レビューが重い PR は、コードが難しいから重いのではなく、**diff だけでは復元できない情報が本文に書かれていない**から重くなる。レビュアーは欠けた情報を自力で組み立てる（旧実装との対応付け、失敗経路の分岐表、読む順番の決定、どこが実測済みかの切り分け）作業を負う。

このスキルは自分の diff を走査して、その「レビュアーが自力で組み立てる情報」を洗い出し、PR 本文の追記案にする。

`pr-format` は本文の**形式**（タイトル・セクション構成）を担当する。こちらは本文に**何を書くか**を決める。両方使う。

## 使うとき

- `gh pr create` / `gh pr edit` の直前
- PR 本文を書き終えたとき
- レビューが重いと指摘された PR の本文を後から補強するとき

使わないとき: 他人の PR のレビュー（`review-strict` / `code-review` を使う）。

## 手順

### 1. base を決めて diff を取る

base は PR の向き先。applynow は `origin/dev`、applynow-scraper は `origin/stg`。既存 PR なら `gh pr view --json baseRefName --jq .baseRefName` で確認する。

```bash
BASE=origin/dev
git fetch -q origin && git diff --numstat $(git merge-base $BASE HEAD)..HEAD
```

以降の `$DIFF` は `git diff $(git merge-base $BASE HEAD)..HEAD` を指す。

### 2. 7項目を走査する

各項目は「兆候 → 本文のどのセクションに何を書くか」の対応で読む。検出コマンドは当たりを付けるためのもので、判断は diff を読んで行う。

#### (1) 目的が複数ある（分割候補）

兆候: 独立したレイヤーを同時に触っている。インフラ定義（terraform / k8s / CI 設定）とアプリコードが同じ PR にある。本文に「追加対応として」「あわせて」「ついでに」と書いている。コミットメッセージの要約が2種類以上の目的に分かれる。

```bash
git log --oneline $(git merge-base $BASE HEAD)..HEAD
git diff --name-only $(git merge-base $BASE HEAD)..HEAD | sed 's|/.*||' | sort -u
```

対応: 目的ごとに PR を分ける。分けられない場合は**「変更内容」の冒頭に revert 単位を書く**（どのコミットがどの目的か、どれが必須でどれが任意か）。目的が混在した PR は、レビュアーが「必須の変更」と「任意の変更」の切り分けを自力でやることになる。

#### (2) 実質全書き換えのファイル

兆候: 削除行が元ファイルの半分を超える。diff は「旧のどこが新のどこへ行ったか」を示さないので、レビュアーは旧実装と新実装を並べて読み直す。

```bash
git diff --numstat $(git merge-base $BASE HEAD)..HEAD | awk '$3!="-"{print $2, $3}' | while read del f; do
  orig=$(git show $BASE:"$f" 2>/dev/null | wc -l); [ -n "$orig" ] && [ "$orig" -gt 0 ] && [ "$del" -gt $((orig/2)) ] && echo "$f: -$del / $orig 行"
done
```

対応: **「変更内容」のネストに旧→新の対応表**を書く。消した関数・処理がどこへ行ったか（別関数へ移動 / 共通基盤へ移動 / 不要になって削除）を1行ずつ。「不要になって削除」はその理由も。

#### (3) 共通基盤と呼び出し元の同時変更

兆候: mixin / base クラス / 共通モジュール / ユーティリティと、その呼び出し元を同じ PR で変えている。呼び出し元は基盤の新メソッドを理解しないと読めず、基盤の正しさは呼び出し元の使い方に依存する。相互依存でレビューを始めるエントリポイントがない。

```bash
git diff --name-only $(git merge-base $BASE HEAD)..HEAD | grep -iE 'mixin|base|common|shared|util|abstract'
```

対応: **「レビュー観点」に読む順番**を書く。「基盤の新メソッドの意味 → 呼び出し元のフロー → 呼び出し規約（暗黙の契約）」のように、ファイル:行 付きで3〜6ステップ。基盤側に呼び出し元への要求（このキーを持つ dict を渡す、このリストは末尾から pop する 等）があるならそれも明記する。

#### (4) 失敗経路・分岐の増加

兆候: 例外クラス・`except` 分岐・早期 return が増えている。経路が3つを超えると、レビュアーは分岐表を自分で書き起こさないと網羅できない。

```bash
$DIFF | grep -cE '^\+[[:space:]]*(raise|except|throw|catch|return[[:space:]]|if .*:$)'
$DIFF | grep -E '^\+[[:space:]]*(raise|except|throw|catch) ' | sort -u
```

対応: **「変更内容」に失敗経路の分岐表**を書く。「どの失敗 → リトライするか → 通知するか → 次に何をするか」を経路ごとに1行。複数の入口（通常フローとエラーコールバック等）が同じ処理に合流するなら、合流点も書く。

#### (5) 閾値・時間定数の分散

兆候: timeout / limit / retry / max などの閾値が、複数ファイル・複数レイヤー（インフラ定義・アプリ定数・ライブラリ設定）に散っている。どの閾値がどこで発火してどの経路に落ちるかの組み合わせが増え、レビュアーが状態機械を頭の中で組むことになる。

```bash
$DIFF | grep -nE '^\+.*([Tt]imeout|TIMEOUT|_SECONDS|_MS|[Ll]imit|LIMIT|[Rr]etr(y|ies)|RETRY|max_|MAX_)'
```

対応: まず**参照元を一本化できないか検討する**（片方が他方から導出できるなら定数を1つにする）。できない場合は **「変更内容」に閾値の一覧**を書く。値・単位・どこで設定してどこで発火するか・超過したらどの経路に落ちるかを1行ずつ。定数名には単位を入れる（`_SECONDS` / `_MS`）。

#### (6) 新規の純関数にテストがない

兆候: 引数だけで結果が決まる関数（計算・判定・分担・URL やパスの組み立て・フォーマット変換）を追加したのに、テストの diff にその名前が出てこない。テストしやすい部分にテストがないと、レビュアーは手で検算する。

```bash
$DIFF | grep -E '^\+[[:space:]]*(def|function|func|const .*=>) ' | sed 's/^\+[[:space:]]*//'
git diff --name-only $(git merge-base $BASE HEAD)..HEAD | grep -iE 'test|spec'
```

対応: テストを書く。リポジトリにテスト基盤がない等で書けない場合は、**「動作確認」に対象の関数名と検算内容**（どの入力でどの出力を目視確認したか）を書く。テスト基盤がないこと自体も書く。

#### (7) 未検証の経路

兆候: 「動作確認」のチェック項目に対応しない経路が diff にある。エラーハンドリング・コールバック・再送出・フォールバックは特に落ちやすい。並列実行・分担のような環境依存の挙動も、ローカルでは踏めていないことが多い。

```bash
$DIFF | grep -nE '^\+[[:space:]]*(except|catch|errback|raise .*from|fallback)'
```

対応: **「動作確認」に未検証の経路を明示**する。「未検証」と書く。書かないと、レビュアーは実測済みの経路と読んだだけの経路を自力で切り分ける。検証できない理由（本番でしか踏めない・外部サービス依存）があるならそれも書く。

### 3. 出力

次の3つをこの順で出す。

```markdown
## 分割の判断

分けるべきか、分けないならその理由。分けない場合は revert 単位。

## 本文に足りないもの

- 検出した項目 → 何を書くべきか（該当なしの項目は挙げない）

## 追記案

そのまま PR 本文に貼れる Markdown。`pr-format` のどのセクションに入れるかを見出しで示す。
```

追記案は実際に貼れる完成形で出す。「〜を書くとよい」ではなく、中身を埋めたものを出す。

分量の規律:

- 追記案は本文に貼る前提。**本文が diff より長くなったら情報を絞る**。表は列を4つ程度までにし、レビュー判断に効かない列は落とす
- 旧→新の対応表は、書き換えファイルが複数あるなら影響の大きいものに絞る。全ファイルを網羅しない
- **分割すると決めたなら、追記案は分割後の PR 単位で出す**。分割前の1本に全部を詰めた本文を作らない

## よくある失敗

- **検出コマンドの結果だけ報告して終わる** — 数字を出すのが目的ではない。diff を読んで判断し、追記案の中身まで書く。
- **7項目を全部並べる** — 該当しない項目は挙げない。該当ゼロなら「追記不要」で終わる。
- **「レビュー観点」に丸投げする** — 「複雑なので注意して見てください」は情報ではない。読む順番・分岐表・未検証リストという具体物にする。
- **diff を読まずに本文だけ見る** — 本文に書かれていないものを探すスキルなので、diff が一次情報。
- **分割提案を省く** — 一番効くのが分割。本文を厚くすることで分割を回避しない。
- **検出した全項目を最大の粒度で書き出す** — 追記案は読まれてはじめて効く。網羅性より、レビュアーが最初の30分で使う情報を優先する。
