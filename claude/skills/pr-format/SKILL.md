# PR フォーマット

PR のタイトルと本文はこのフォーマットで書く。リポジトリに `.github/PULL_REQUEST_TEMPLATE.md` がある場合はそちらを優先し、このフォーマットは不足セクションの補完に使う。

## タイトル

- 日本語1行・50字以内。変更の要約を「〜を追加」「〜を修正」「〜に統一」の形で書く
- `feat:` 等のプレフィックスは付けない
- タイトルは PR のタイトル欄のみに書き、本文冒頭に H1 として繰り返さない

## 本文

本文は次の5セクションをこの順で並べたものとする:

```markdown
## 概要

何を・なぜを2〜3文で。

## 変更内容

- 変更点の要点（トップレベルは1項目1行。ここだけ読めば変更の全体像が掴めるようにする）
  - その項目の詳細・実装上の判断とその理由は、ネストした箇条書きに分けて書く

## 背景・経緯

課題や動機。チケット / issue へのリンク。

## 動作確認

- 実行したテスト・確認手順と結果

## レビュー観点

- 特に見てほしい箇所・自信がない箇所
- 議論したい設計判断
```

## スクリーンショット（UI 変更時）

UI に見た目の変更がある PR では、「変更内容」の後に `## スクリーンショット` セクションを追加し、変更後の各画面のスクリーンショットを表形式で載せる。

- 撮影はヘッドレスブラウザ（Playwright 等）で dev サーバーの実画面を撮る。開発ツールバーの写り込みは除去する
- **画像をリポジトリにコミットしない。** PR 本文に載せるためだけの画像はリポジトリに不要なゴミを増やす。blob は履歴に永久に残り、後から取り除くには履歴の書き換え（オープン PR がある間は禁止）が必要になる
- 本文には撮影ファイルへのローカル参照（`![alt](./path.png)`）を書き、`gh pr create` / `gh pr edit` に同じパスを `--attach` で渡す。gh がアップロードして本文中の参照を実際の URL に書き換える
  - `--attach` は gh 2.99.0 以降・GitHub.com / GHEC のみ。gh が古い場合や GHES では、画像セルを空にした表だけを本文に置き、撮影ファイルのパスを画面名と対応づけて伝えて、GitHub の編集画面への貼り付けはユーザーに任せる
  - alt text はパスの後ろに `#` で続ける（`--attach './login.png#ログインエラー時の表示'`）。省略時はファイル名が使われる
  - 一部のアップロードが失敗しても成功分で PR は作成・更新され、終了コードだけ非ゼロになる。失敗時は出力を確認する

```markdown
| 画面 | |
|---|---|
| メンバー設定（一括招待ボタンを追加） | ![メンバー設定](./member-settings.png) |
| 一括招待の履歴一覧 | ![一括招待の履歴一覧](./invite-history.png) |
```

対応する実行例:

```bash
gh pr create --title '...' --body-file body.md \
  --attach './member-settings.png#メンバー設定画面' \
  --attach './invite-history.png#一括招待の履歴一覧'
```

## ルール

- 変更内容は「トップレベル＝要点、ネスト＝詳細」の2階層で書く。要点と詳細を同じ階層に混ぜない。diff の詳細は PR の Files タブで読めるので、本文には判断と構造だけを書く
- 省略できるのは「背景・経緯」（自明な場合）と「レビュー観点」（特にない場合）の2つのみ
- 「動作確認」は必須。何も実行していない場合は「なし（ドキュメントのみの変更のため）」のように理由付きで書く。実行していない確認を書かない
- 本文は日本語の常体で書く。敬語・丁寧語は使わない（「〜します」→「〜する」、「〜ください」→「〜する」、「確認していただきたい」→「確認したい」）
- 本文で変数名・略称を使うなら、初出で実体（パス・値）との対応を示す。表やコード例の中で急に使わない。同じ名前が複数の実体を指す場合は対応表にする
- **「レビュー観点」には現在の状態だけを書く。** 「当初 X だったが Y に変えた」という経緯は書かない。レビュアーが判断に使うのは今どうなっているかであって、捨てた設計ではない（経緯を残したいなら設計 doc 側に置く）。見出しも「〜にした判断」ではなく「〜になっている」と現在形にする
- **「レビュー観点」に置くのは判断を求める項目だけ。** 件数・既存データの状況・影響範囲のような「知っておいてほしい事実」は「背景・経緯」か「変更内容」へ移す。観点に事実を並べると、レビュアーは全部について判断を求められていると受け取る
- 実装中に使っていた内輪の呼び名（造語・社内略称）を本文に持ち込まない。何が起きるかがそのまま読める表現にする（例:「デュアルライト」→「新旧両列への書き込み」）
- Draft PR でも本文は最初から書く
