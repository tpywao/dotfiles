# 選別つきレビュー

## 概要

`code-review` は指摘を広く拾うが、その一覧をそのまま出すと、変更が持ち込んでいない問題、運用ミスでしか起きないバグ、次の作業で意味がなくなる指摘、裏の取れていない推測が混ざる。このスキルは `code-review` の結果を選別・裏取りし、残った指摘だけを決まった形で示して、最後の操作（PR への投稿、作業中の差分の修正）までつなぐ。

対象の指定は `code-review` と同じ（PR 番号・ブランチ名・引数なし・パス）。レベルや `--max-findings` などの引数は `code-review` へそのまま渡す。

## 手順

### 1. 対象を判定し、前提を集める

対象ごとに、レビューする版（以降 head）・比べる相手（以降 `BASE`）・前提の情報源・最後の操作を決める。

| 対象 | head | BASE | 前提の情報源 | 最後の操作 |
|---|---|---|---|---|
| PR 番号・URL | `headRefOid` | PR の base ブランチとの merge-base | PR 本文、コミットメッセージ、チケット | 投稿 |
| ブランチ名 | `git rev-parse <ブランチ>` | 既定ブランチ（リポジトリの指示ファイルに開発用の base があればそれ）との merge-base | ブランチ名やコミットのチケット番号、コミットメッセージ | 報告し、直すか確認 |
| 引数なし | 作業ツリー（`HEAD` に未コミットの変更を足したもの） | upstream（無ければ既定ブランチ）との merge-base | 現在のブランチ名、会話の文脈 | 報告し、直すか確認 |
| パス | なし | なし | 対象コードのコメント、関連する設計 doc | 報告のみ |

```bash
# PR
gh pr view <N> --json baseRefName,headRefOid,body,author
git fetch origin pull/<N>/head
BASE=$(git merge-base origin/<baseRefName> <headRefOid>)

# ブランチ
git fetch origin <既定ブランチ>
BASE=$(git merge-base origin/<既定ブランチ> <ブランチ>)

# 引数なし
BASE=$(git merge-base @{upstream} HEAD 2>/dev/null || git merge-base <既定ブランチ> HEAD)
```

引数なしの `BASE` は、`code-review` が引数なしで見る範囲（`@{upstream}...HEAD`、upstream が無ければ `main...HEAD` に、作業ツリーの変更を足したもの）に合わせる。`A...B` の差分は A と B の merge-base から B までの差分なので、反証と `code-review` が同じ変更を見ることになり、手順 3 でコミット済みの変更が既存と判定されることもない。push 済みのブランチでは upstream が自分のリモートブランチになるので、まだ push していないコミットと作業ツリーの変更だけが対象になる。ブランチ全体を見たいときはブランチ名を渡す。

前提として拾うのは次の 2 つ:

- チケット番号が取れたら、使えるチケット管理ツール（MCP やスキル）で本文を読む。
- **移行の段階と次の作業の予定**。PR 本文やコード中の「別リリースで削除」「移行期間中」「TODO」などの記述から拾い、「次の作業で消えるもの」を手順 3 で判定できるようにする。

### 2. 反証と `code-review` を並行して走らせる

レビュー対象の変更そのものを `skeptic` で反証する。`code-review` の指摘や手順 3・4 の選別の判断は渡さない。渡すと反証が選別結果の確認にとどまり、`code-review` が拾わなかった問題を拾えない。結果に依存しないので、`code-review` を待たずに始める。

1. 対象をスクラッチパッドの新しいファイルに保存する。先頭にリポジトリのパス、手順 1 で決めた head と `BASE`、作業ツリーの `HEAD` を書き、反証する側が周辺のコードを自分で読めるようにする。作業ツリーがレビュー対象の head と一致するとは限らない（他人の PR を手元のブランチのまま見るなど）ので、head と `BASE` は値として書く。引数なしは head を「作業ツリー（`HEAD` に未コミットの変更を足したもの）」と書く。
   - **PR**: `gh pr view <N> --json number,title,body,baseRefName,headRefOid,commits,files,url` と `gh pr diff <N>` の全文
   - **ブランチ**: ブランチ名、`git log ${BASE}..<ブランチ>` のコミットメッセージ、`git diff ${BASE} <ブランチ>` の全文
   - **引数なし**: 現在のブランチ名、`git log ${BASE}..HEAD` のコミットメッセージ、`git diff ${BASE}` の全文（コミット済みと未コミットの変更の両方が入る）、`git ls-files --others --exclude-standard` で挙がる未追跡の新規ファイルの中身（`git diff` には出ない）
   - **パス**: 保存せず、そのパスを次でそのまま渡す。先頭の情報も書かない（絶対パスでどのリポジトリかは分かる）
2. 先に `skeptic` スキルを呼び、引数にはこのファイル（パス指定ならそのパス）だけを渡す。レビューの経緯は渡さない。`skeptic` スキルの手順どおり、エージェントは起動したら完了を待たずに戻るので、起動を確かめたらすぐ次へ進む。環境によってエージェントが完了まで戻らないときは、`skeptic` のあとに `code-review` が順に走るだけで、手順はそのまま進められる。
   - `skillOverrides` で無効にされていて呼べない（`disabled for model invocation`）ときは、エージェントを直接呼んで迂回しない。ユーザーに `/skeptic <ファイルのパス>` の実行を依頼し、反証の結果を待たずに次へ進む。このときは `skeptic` スキル自身が報告の全文を出すが、ユーザーが自分で呼んだ結果なのでそのままにする。このスキルは全文を繰り返さず、指摘を選別の材料にだけ使う。
3. 続けて、同じ対象と引数で `code-review` スキルを呼び、結果の一覧を待つ。ブランチ名を渡したとき、`code-review` は何と比べるかを自分で決めるので、`BASE` と範囲がずれることがある。範囲は手順 3 で `BASE` に揃える。
4. `code-review` の実行中や手順 3・4 の途中に `skeptic` の報告が届いたら、`skeptic` スキルの手順をその場で進め、届いた指摘をその時点で手順 3・4 にかける。このスキルが `skeptic` を呼んだときの規則の扱いは次のとおり（`skeptic` スキルの「呼び出し元の決まりを優先する」による）。
   - 引き継ぐ: エージェントへの依頼、生成の経緯を渡さないこと、部分報告への続行指示、照合を行うこと
   - 引き継がない: 報告と照合の結果を全文そのまま提示すること、トリアージをしないこと。報告は選別の材料にし、範囲外・除外にした指摘も手順 5 で理由と一緒に示して、どの指摘も黙って落とさない
   - 深刻度 高 の指摘: 届いた時点で、指摘を 1 文にしたものと深刻度だけを先にユーザーへ伝える。選別には手順 3 でほかの指摘と一緒にかける
   - 報告の保存: 照合の手順で報告を抜き出したら、反証 1 回につき 1 つの報告ファイルに届いた順で追記する。報告ファイルは反証を始めるたびに新しく作り、既存のファイルには追記しない（名前は `<スクラッチパッド>/skeptic-report-$(date +%Y%m%d-%H%M%S).md` のように時刻を入れる）。同じセッションで修正後にもう一度レビューしても、前回の指摘が混ざらないようにするため。照合の結果も同じファイルに追記する。部分報告ごとにできるファイルはそのまま照合に使い、手順 5 で添えるのはこの報告ファイルにする

### 3. 指摘を選別する

`code-review` と `skeptic` の指摘を合わせて選別する。先に、指す行も原因も `git diff ${BASE} <head>`（引数なしなら `git diff ${BASE}`）の変更行に含まれない指摘を「範囲外（レビュー範囲の外）」に回す。`code-review` が `BASE` とは別の基準で拾ったもので、下の発生元の判定にはかけない。差分の外の行を指していても、原因が変更行にあるものは残して判定にかける（手順 6 で原因の行に置く）。パス指定は `BASE` がないのでこの絞り込みをしない。残りのうち同じ内容の指摘は 1 つにまとめ、指摘ごとに出所（`code-review` / `skeptic` / 両方）を書く。指摘ごとに次の 5 つを判定し、表にまとめる。

1. **発生元**: `git show ${BASE}:<path>` で変更前の同じ箇所を読み、変更が持ち込んだか（持ち込み）、変更前から同じか（既存）を決める。変更前から同じなら、変更は属性名を差し替えただけでも既存とする。パス指定は BASE がないので判定しない。
2. **発生条件**: 通常の操作 / 外部からのリクエスト / 既存のデータ / 運用ミス（鍵や環境変数の設定ミス、手順の途中など）/ 仮定のコード（今は存在しない呼び出し方）のどれで起きるか。
3. **状態に至る経路**: 問題の起きる値（空文字、NULL など）が、実際にどの操作で作られるかを確かめる。フレームワークの既定の挙動で発生のしやすさが逆転することがある（例: Django の `ModelForm` は `null=True` の `CharField` の空欄を `None` で保存する）。
4. **次の作業で消えるか**: 手順 1 で拾った予定と照らし、次の作業で意味がなくなる指摘か（移行用コードへのテスト不足など）。
5. **根拠**: 指摘の根拠がリポジトリの規約か、個人の指示ファイル（`~/.claude/CLAUDE.md` など）か。

振り分け:

- **残す**: 持ち込みで、通常の操作・外部からのリクエスト・既存のデータで起きるもの。設計や性能の提案は「提案」として残す。
- **範囲外**: 既存のもの。
- **除外**: 運用ミス・仮定のコードでしか起きないもの、次の作業で消えるもの、根拠が個人の指示ファイルだけのもの。

`skeptic` の指摘も `code-review` の指摘と同じ基準で振り分ける。範囲外・除外にしても手順 5 で指摘の原文と理由を示すので、作り手に都合のよい判定があってもユーザーが一覧で見つけて戻せる。

### 4. 残した指摘を裏取りする

- head（引数なしなら作業ツリー）のコードで、指摘した行番号と内容が一致するか読む。
- ライブラリの挙動を根拠にする指摘は、ソースかリポジトリ内のコメント・テストを出典として付ける。取れなければ「未確認」と書き、断定しない。
- 発生件数がデータ次第のものは「未確認」とし、数え方（どの列がどの値の件数か）を添える。
- 再現方法に書く URL・コマンドは、ルーティングなどの定義から取る。URL 名や関数名から推測しない。

### 5. 提示する

残した指摘を、重い順に次の形で並べる。

```markdown
### <番号>. <一行の要約>（`<path>:<line>`）
- **出所**: `code-review` / `skeptic` / 両方。`skeptic` の報告の照合で矛盾ありとされたものはその内容も書く
- **問題点**: 何が起きて、誰がどう困るか
- **原因**: それが起きる仕組み（コードの経路）
- **発生のしやすさ**: 高 / 中 / 低 / 未確認 と、その根拠（発生条件・状態に至る経路）
- **修正のしやすさ**: 易 / 中 / 難 と、修正案の要点
- **再現方法**: 手順を番号付きで（バグでない指摘は「確認方法」）
- **重要度**: 必須 / 条件付き / 任意 と、その理由。必須は、直さずに進めると変更の目的を損なうもの（PR・ブランチならマージ前、作業中の差分ならコミット前に直す）。条件付きは、何が分かれば必須になるか（仕様の確認先など）も書く
```

一覧の冒頭に、必須・条件付き・任意それぞれの件数を書く。

その後に「範囲外」「除外」の一覧を続ける。指摘ごとに、出所、指摘の内容を 1 文、範囲外・除外にした理由を 1 文で書く。指摘の内容は自分で要約せず、出所の原文をそのまま載せる。`skeptic` の指摘は報告の「指摘」欄、`code-review` の指摘は指摘ごとに出る 1 文の要約を使い、両方なら両方を載せる。選別した本人が要約すると、論点をずらしたり弱めたりして除外の判定に合わせられるため。自分で書くのは理由の 1 文だけにする。今回の変更で直さなくても別のチケットで扱う可能性があるので、ユーザーが一覧だけを読んで、戻すか別に切り出すかを決められるようにする。

`skeptic` の報告がこの時点で届いていなければ、待って手順 3・4 にかけてから提示する。ただし手順 2 で `skeptic` を呼べずユーザーに実行を頼んだときは待たない。反証は未実施（`/skeptic` の実行待ち）と冒頭に書いて提示し、あとで報告が届いたら、その指摘を手順 3・4 にかけて追加分として示す。報告の全文はこの一覧には載せず、手順 2 の 4 の報告ファイルのパスだけを添える。ユーザーは範囲外・除外の一覧を、このファイルの手を加えていない報告と見比べられる。

提示のあと、残した指摘から外すもの、範囲外・除外から戻すもの、別のチケットに切り出すものをユーザーに尋ね、判断を選別結果に反映してから、どれを投稿するか（PR）・直すか（作業中の差分・ブランチ）を尋ねる。

### 6. 最後の操作

**PR**: 選ばれた指摘ごとにコメントの文面を作って見せ、判定（Approve / Comment / Request changes）と本文を確認してから、1 回のレビューとしてまとめて投稿する。文面は、冒頭に結論と修正の方向、続けて番号付きの節（何が起きるか / 再現手順 / 修正案 / 補足）にする。

インラインコメントは diff の hunk に含まれる行にしか置けない。指摘した行が hunk の外にあるとき（変更していない呼び出し側が壊れるなど）は、原因になった変更行にコメントを置き、影響が出る場所（`<path>:<line>`）を文面に書く。原因が削除した行なら、`side: "LEFT"` と変更前の行番号でその行に置く。置ける変更行が無い指摘（足りないマイグレーションやテスト、設計の提案など）だけをレビュー本文に書く。

レビュー本文にインラインコメントの内容は繰り返さない。インラインコメントがあるときは「インラインで n 件コメントしたので確認をお願いします」と一言だけ添える。本文に書く指摘があるときは、その一言に「加えて以下 m 件」と続けて、指摘を並べる。インラインコメントが無く本文にだけ指摘があるときは、一言を書かずに指摘だけを並べる。下書きのあとに投稿する指摘を絞ったときは、n と m をそれに合わせる。

```bash
# 本文は JSON ファイルに書いてから渡す（コマンド引数に長文を埋め込まない）
gh api repos/<owner>/<repo>/pulls/<N>/reviews --method POST --input review.json
```

`review.json` には `commit_id`（head の SHA）・`event`・`body`・`comments`（`path` / `line` / `side` / `body`）を入れる。`side` は追加した行と変更のない行なら `"RIGHT"`（`line` は変更後の行番号）、削除した行なら `"LEFT"`（`line` は変更前の行番号）にする。`line` は diff の hunk に含まれる行でなければ受け付けられない。

**ブランチ・作業中の差分**: 選ばれた指摘を直す。直したあとは、その指摘の再現方法で直ったことを確かめる。

## よくある間違い

- **diff だけを見て発生元を決める** → 変更前の同じ箇所を `git show ${BASE}:<path>` で必ず読む。差分の行に出ていても、属性名の差し替えだけなら既存。
- **zsh で `git show $BASE:app/...` と書く** → `$BASE:a` が修飾子として展開されパスが壊れる。`${BASE}` と書く。
- **発生のしやすさを指摘文の言い分のまま書く** → 手順 3 の「状態に至る経路」を確かめてから書く。
- **ユーザーの確認なしに投稿する** → 投稿・判定は必ず文面と一緒に確認を取る。
