# 選別つきレビュー

## 概要

`code-review` は指摘を広く拾うが、その一覧をそのまま出すと、変更が持ち込んでいない問題、運用ミスでしか起きないバグ、次の作業で意味がなくなる指摘、裏の取れていない推測が混ざる。このスキルは `code-review` の結果を選別・裏取りし、残った指摘だけを決まった形で示して、最後の操作（PR への投稿、作業中の差分の修正）までつなぐ。

対象の指定は `code-review` と同じ（PR 番号・ブランチ名・引数なし・パス）。レベルや `--max-findings` などの引数は `code-review` へそのまま渡す。

## 手順

### 1. 対象を判定し、前提を集める

対象ごとに、比べる相手（以降 `BASE`）・前提の情報源・最後の操作を決める。

| 対象 | BASE | 前提の情報源 | 最後の操作 |
|---|---|---|---|
| PR 番号・URL | PR の base ブランチとの merge-base | PR 本文、コミットメッセージ、チケット | 投稿 |
| ブランチ名 | 既定ブランチ（リポジトリの指示ファイルに開発用の base があればそれ）との merge-base | ブランチ名やコミットのチケット番号、コミットメッセージ | 報告し、直すか確認 |
| 引数なし | `HEAD` | 現在のブランチ名、会話の文脈 | 報告し、直すか確認 |
| パス | なし | 対象コードのコメント、関連する設計 doc | 報告のみ |

```bash
gh pr view <N> --json baseRefName,headRefOid,body,author
git fetch origin pull/<N>/head
BASE=$(git merge-base origin/<baseRefName> <headRefOid>)
```

前提として拾うのは次の 2 つ:

- チケット番号が取れたら、使えるチケット管理ツール（MCP やスキル）で本文を読む。
- **移行の段階と次の作業の予定**。PR 本文やコード中の「別リリースで削除」「移行期間中」「TODO」などの記述から拾い、「次の作業で消えるもの」を手順 3 で判定できるようにする。

### 2. `code-review` を実行する

同じ対象と引数で `code-review` スキルを呼び、結果の一覧を待つ。

### 3. 指摘を選別する

指摘ごとに次の 5 つを判定し、表にまとめる。

1. **発生元**: `git show ${BASE}:<path>` で変更前の同じ箇所を読み、変更が持ち込んだか（持ち込み）、変更前から同じか（既存）を決める。変更前から同じなら、変更は属性名を差し替えただけでも既存とする。パス指定は BASE がないので判定しない。
2. **発生条件**: 通常の操作 / 外部からのリクエスト / 既存のデータ / 運用ミス（鍵や環境変数の設定ミス、手順の途中など）/ 仮定のコード（今は存在しない呼び出し方）のどれで起きるか。
3. **状態に至る経路**: 問題の起きる値（空文字、NULL など）が、実際にどの操作で作られるかを確かめる。フレームワークの既定の挙動で発生のしやすさが逆転することがある（例: Django の `ModelForm` は `null=True` の `CharField` の空欄を `None` で保存する）。
4. **次の作業で消えるか**: 手順 1 で拾った予定と照らし、次の作業で意味がなくなる指摘か（移行用コードへのテスト不足など）。
5. **根拠**: 指摘の根拠がリポジトリの規約か、個人の指示ファイル（`~/.claude/CLAUDE.md` など）か。

振り分け:

- **残す**: 持ち込みで、通常の操作・外部からのリクエスト・既存のデータで起きるもの。設計や性能の提案は「提案」として残す。
- **範囲外**: 既存のもの。参考として 1 行で示す。
- **除外**: 運用ミス・仮定のコードでしか起きないもの、次の作業で消えるもの、根拠が個人の指示ファイルだけのもの。理由を 1 行で示す。

### 4. 残した指摘を裏取りする

- head（引数なしなら作業ツリー）のコードで、指摘した行番号と内容が一致するか読む。
- ライブラリの挙動を根拠にする指摘は、ソースかリポジトリ内のコメント・テストを出典として付ける。取れなければ「未確認」と書き、断定しない。
- 発生件数がデータ次第のものは「未確認」とし、数え方（どの列がどの値の件数か）を添える。
- 再現方法に書く URL・コマンドは、ルーティングなどの定義から取る。URL 名や関数名から推測しない。

### 5. 反証にかける

1. 選別結果をスクラッチパッドの新しいファイルに書く。中身は次の 3 つ。
   - **対象の特定情報**: リポジトリのパス、PR 番号かブランチ名、head SHA、`BASE`。反証する側が自分でコードを読めるようにする
   - **残した指摘**: 手順 6 の 5 項目の形で全文
   - **範囲外・除外**: 指摘ごとに判定と根拠（`BASE` のどの行で同じだったか、どの発生条件と判定したか）
2. `skeptic` スキルを呼び、引数にはこのファイルのパスだけを渡す。生成の経緯は渡さない。
   - `skillOverrides` で無効にされていて呼べない（`disabled for model invocation`）ときは、エージェントを直接呼んで迂回しない。ユーザーに `/skeptic <ファイルのパス>` の実行を依頼して待つ。
3. 以降は `skeptic` スキルの手順（反証と、報告の照合）に従い、報告を手を加えずに受け取る。

範囲外・除外の判定も反証にかける。「変更前から同じ」「運用ミスでしか起きない」も主張で、外れると本当のバグを落とす。

### 6. 提示する

残した指摘を、重い順に次の形で並べる。

```markdown
### <番号>. <一行の要約>（`<path>:<line>`）
- **問題点**: 何が起きて、誰がどう困るか
- **原因**: それが起きる仕組み（コードの経路）
- **発生のしやすさ**: 高 / 中 / 低 / 未確認 と、その根拠（発生条件・状態に至る経路）
- **修正のしやすさ**: 易 / 中 / 難 と、修正案の要点
- **再現方法**: 手順を番号付きで（バグでない指摘は「確認方法」）
```

その後に「範囲外」「除外」の一覧を、指摘ごとに 1 行（要約と理由）で続ける。

続けて `skeptic` の報告と照合結果を全文そのまま載せる。要約・反論・弁護はしない。反証を受けて、どの指摘を残す・外す・範囲外から戻すかをユーザーに尋ね、判断を選別結果に反映してから、どれを投稿するか（PR）・直すか（作業中の差分・ブランチ）を尋ねる。

### 7. 最後の操作

**PR**: 選ばれた指摘ごとにコメントの文面を作って見せ、判定（Approve / Comment / Request changes）と本文を確認してから、1 回のレビューとしてまとめて投稿する。文面は、冒頭に結論と修正の方向、続けて番号付きの節（何が起きるか / 再現手順 / 修正案 / 補足）にする。

```bash
# 本文は JSON ファイルに書いてから渡す（コマンド引数に長文を埋め込まない）
gh api repos/<owner>/<repo>/pulls/<N>/reviews --method POST --input review.json
```

`review.json` には `commit_id`（head の SHA）・`event`・`body`・`comments`（`path` / `line` / `side: "RIGHT"` / `body`）を入れる。`line` は diff の hunk に含まれる行でなければ受け付けられない。

**ブランチ・作業中の差分**: 選ばれた指摘を直す。直したあとは、その指摘の再現方法で直ったことを確かめる。

## よくある間違い

- **diff だけを見て発生元を決める** → 変更前の同じ箇所を `git show ${BASE}:<path>` で必ず読む。差分の行に出ていても、属性名の差し替えだけなら既存。
- **zsh で `git show $BASE:app/...` と書く** → `$BASE:a` が修飾子として展開されパスが壊れる。`${BASE}` と書く。
- **発生のしやすさを指摘文の言い分のまま書く** → 手順 3 の「状態に至る経路」を確かめてから書く。
- **ユーザーの確認なしに投稿する** → 投稿・判定は必ず文面と一緒に確認を取る。
